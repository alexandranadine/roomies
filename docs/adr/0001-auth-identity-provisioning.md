# ADR 0001: Provision canonical Users for authentication identities

- Status: Accepted
- Date: 2026-09-10

## Context

Roomies has three separate identity concepts:

- `User` is the canonical product identity.
- `AuthIdentity` is Better Auth's authentication identity and profile.
- `Membership` is tenure-specific Home authorization context.

Better Auth is not authoritative for Home roles or capabilities. Authorization
must continue to read current Membership state rather than copying it into auth
identity or session rows.

The persistence invariant is asymmetric: every committed AuthIdentity has
exactly one canonical User with the same UUID, while a User may remain without
an AuthIdentity after authentication infrastructure or credentials are
deleted.

## Decision

`auth_identities.id` and `users.id` are PostgreSQL native UUID columns with the
same value. `auth_identities.id` has an immediate, non-deferrable foreign key to
`users.id` with `ON DELETE RESTRICT` and `ON UPDATE RESTRICT`. There is no
foreign key or cascade from User to AuthIdentity.

A narrowly scoped `BEFORE INSERT FOR EACH ROW` trigger on
`public.auth_identities` calls
`public.provision_user_for_auth_identity()`. The function:

- runs as `SECURITY INVOKER` with a controlled search path;
- inserts `NEW.id` into `public.users`;
- initializes only the mandatory `updated_at` structural column and relies on
  the existing `created_at` database default;
- uses a strict insert with no conflict suppression or exception swallowing;
- creates no Home, Membership, role, activity, notification, or other product
  state.

The auth identity UUID is generated by the PostgreSQL
`pg_catalog.gen_random_uuid()` column default before the trigger executes.
UUIDv4 is allowed for auth-provisioned Users. Existing general User, Home, and
Membership UUIDv7 policy is unchanged.

Auth accounts and sessions reference AuthIdentity and cascade on AuthIdentity
deletion so authentication infrastructure can be removed cleanly. Verification
rows have no product-domain relationship. Deleting an AuthIdentity leaves its
canonical User; deleting that User while the AuthIdentity exists is rejected.

Prisma 8 is the sole schema and migration authority. All representable auth
tables, columns, indexes, and foreign keys belong in the authoritative Prisma
contract. The function and trigger are reviewed custom operations inside the
attested Prisma migration package. Better Auth migration tooling must not own
the production schema.

Better Auth runtime will use its official direct PostgreSQL integration through
`pg.Pool`. Runtime setup, routes, credentials policy, and authorization are
outside this decision.

## Consequences

An AuthIdentity insert is atomic: PostgreSQL supplies the UUID, the `BEFORE`
trigger inserts the canonical User, the AuthIdentity row is inserted, and the
immediate foreign key is satisfied. Any provisioning failure aborts the
AuthIdentity insert. A pre-existing User with the same UUID causes a strict
collision failure.

This trigger is the only approved Roomies database-trigger exception. No other
product state may be provisioned from it.

## Removal strategy

Replace the trigger once Better Auth exposes a supported application-level
transaction participant that can create the canonical User in the same
database transaction as identity, account, and session creation. The
replacement must preserve the shared UUID, asymmetric invariant, strict
failure behavior, and immediate foreign key before the function and trigger
are removed in an expand-forward migration.
